0.2.1 OWNERSHIP UPDATE
Back up database/config.php/private storage, extract the UPDATE ZIP over the
existing website, and open Enrollments -> Apply database upgrade. This adds the
panel reseller/customer mapping tables; existing records/keys/config remain intact.
Update the EXISTING activation-code worker on its SEPARATE server with the matching
worker ZIP. Do not patch the uploaded reseller portal auth worker or the EPG worker.
The worker reuses the bridge .env already installed; no replacement settings file
or Nginx change is needed when /management/ already works. It needs read-only
access to users.id/username/status and customers.id/member_id in its existing DB.

In Resellers, link each EXISTING workspace to its exact PANEL LOGIN username using
Link panel reseller. The workspace name is prefilled for convenience, but ownership
is based on the verified permanent panel ID, not that name. For NEW workspaces,
fill Existing panel reseller username during creation. Blank means unlinked/manual.
The owner workspace can also be linked to its actual panel account if necessary.

New verified devices automatically get a customer record and reseller assignment;
no per-device admin approval is required for linked active workspaces with capacity.
Unmatched identities, conflicting assignments and removed/rejected devices are not
silently approved. Linked panel identities are unique; transfers are separate work.
Existing 2.0.107-test APKs work without an update. After adding a link, leave a pending
app open a few minutes for its fresh-proof retry. No reactivation/data clearing.

The signed reseller lookup needs PHP cURL with normal verified HTTPS access to
activationworker.extremeiptv.net; never disable TLS verification if it fails.
Target: https://control.fecxbrfzku.net, aaPanel Nginx + PHP 8.3+

IMPORTANT: Real enrollment requires BOTH the activation-worker bridge update and a
management-enabled APK. Old APKs do not automatically appear. Owner approval is
required only for unlinked/conflicting requests; linked verified panel accounts
receive their own device credentials automatically. No branding or reseller

1. BACK UP any existing site/database before deploying. Use a NEW dedicated empty
   MariaDB 10.6+ / MySQL 8.0.16+ database and a user restricted to that database. Prefer
   local socket/127.0.0.1 access; don't expose database ports publicly.
   A hosting-panel port such as 8443 is NOT automatically the MySQL port.
2. Create the PHP site, point DNS at aaPanel, install a valid certificate and force
   HTTPS. Enable PDO/MySQL, mbstring, OpenSSL, fileinfo and cURL for PHP 8.3+.
3. Extract the ZIP INTO /www/wwwroot/control.fecxbrfzku.net (or your chosen app
   folder). src/, database/, public/, storage/ and VERSION should be siblings.
   Delete the uploaded ZIP from the website after extraction.
4. In Website -> Site Directory, set RUNNING DIRECTORY to /public, not the whole
   application directory. PHP open_basedir must allow the APPLICATION PARENT
   directory so PHP can read src/ and storage/. Do not serve that parent publicly.
5. Add deploy/nginx.conf.example to the existing server block/rewrite settings.
   Don't create a duplicate server block or replace aaPanel's TLS/PHP includes.
   Remove a placeholder index.html from public/ if one takes precedence.
6. The install ZIP ALREADY INCLUDES config.php beside public/ (NOT inside public/).
   Open that ONE file in aaPanel File Manager and enter your database password.
   Your host, port, database/user and origin are already filled in. Save and reload.
   No copying, renaming, config.local.php or config.example.php is needed.
   Keep environment = production and origin = https://control.fecxbrfzku.net.
   DSN example: mysql:host=127.0.0.1;port=3306;dbname=YOUR_DB;charset=utf8mb4
   Set your confirmed MySQL host and port here (custom ports are supported).
   Remote SQL requires verified TLS: configure database.ssl_ca with your provider's
   CA certificate when it is not signed by the system trust store. The application
   will not silently disable certificate verification or fall back to plaintext.
   If aaPanel open_basedir blocks /etc/ssl/certs, copy the trusted provider/system
   CA certificate bundle into private storage/ and set ssl_ca to that path. Do not
   disable certificate verification or request the database server's private key.
7. Make storage/ owned/writable by the website PHP user (normally www), mode 700.
   config.php should be owned by that user, mode 600. Application/public
   files may be 644, directories 755. Never use 777. Separate PHP pool users are
   preferable: permissions do not isolate other compromised sites using the same UID.
8. Visit the site. It creates a PRIVATE storage/setup.key. Read that file using
   aaPanel File Manager and enter its key into the setup screen over HTTPS.
   Create your owner account with a strong unique password (14+ characters).
   No default passwords are shipped. Never put the setup key into a URL/chat.
   Setup runs checked migrations and permanently locks first-owner creation in DB.
9. Sign in and create reseller workspaces/customer records. For real app enrollment,
   open Enrollments, download the worker bridge settings, deploy the separate
   activation-worker update, and enable new enrollment after its health check.
   Install the management-enabled testing APK and approve its pending request,
   selecting the correct customer. Optional pre-provisioned records can be attached
   using their record ID. Unapproved/reserved records are not online devices.
10. Add an aaPanel cron task every minute, using your installed PHP CLI path:
    /www/server/php/83/bin/php /www/wwwroot/control.fecxbrfzku.net/cli/console.php maintenance
    CLI PHP must have the same required extensions. Do not run the development
    web server or the local simulator on the public host.

PREFLIGHT / UPGRADES
php cli/console.php preflight   (checks PHP, private storage and database access)
php cli/console.php migrate     (applies pending migrations; back up first)
php cli/console.php maintenance (expires queues/sessions and applies retention)

On upgrades, use the -Update.zip (it deliberately omits config.php). Back up the DB,
config.php and storage/ first, then extract the update in place. The full install
ZIP contains a blank-password config.php and is for new installations only.
Do not delete private configuration, encryption keys or data. If upgrading an
already configured 0.1.0 installation, rename its config.local.php to config.php
once before using the new code; there is only one active config file afterward.
Run migrate with the same PHP version before using new API features. Never edit
an already applied SQL migration; checksum mismatches intentionally stop upgrades.
If DDL fails partway, stop and review/restore the backup; don't drop/reinitialize
tables blindly. Initial setup refuses unrelated populated databases.
For the 0.1.x -> 0.2.0 upgrade, the OWNER can instead use Enrollments -> Apply
database upgrade after backup. This adds enrollment tables/columns and preserves
the existing owner/reseller sessions, customer/device records and private keys.

OWNER PASSWORD RECOVERY (SERVER ACCESS REQUIRED)
Using aaPanel File Manager, create a temporary PRIVATE file outside public/ with
only the new strong password, owned by the PHP/CLI user and mode 600. Then run:
php cli/console.php recover-owner < /private/path/to/password-file
Delete that temporary file immediately afterward. Never put the password in a
command argument/history, chat or URL. This resets only the existing owner and
revokes all owner sessions; it does not erase customer data or regenerate keys.
The original application.key is still required. There is no public recovery API.

BACKUP / RESTORE
Use aaPanel's database backup facility for this dedicated database, and a private
encrypted backup of config.php and storage/. application.key is required
to decrypt data; losing it cannot be repaired by generating a replacement key.
Restore into a NEW private database on a compatible server version, restore the
same private keys/configuration, point the restored config at that DB, and verify
preflight/migrate/login before switching DNS. Do not restore over the live DB as
a test. Restrict backup access and never store SQL/ZIP/config backups in public/.

SECURITY / TROUBLESHOOTING
0.1.2 shows safe, specific MySQL startup diagnostics and the request ID on screen.
It distinguishes refused connections, missing/denied Unix sockets, TLS/certificate
failure, rejected logins, unavailable databases, DNS failures and timeouts without
returning raw driver text, usernames, database names or passwords. Use the update
ZIP on an existing site; it does not replace config.php or initialized storage.
Do not log request bodies, cookies, authorization headers or database passwords.
App errors return a request ID; private PHP logs use that ID without SQL values.
Configure CDN rules to bypass caching for the whole control-center hostname.
Browser cookies are Secure/HttpOnly/SameSite=Strict in production; mutation requests
must come from the exact configured origin and include a session-bound CSRF token.
An SSL-terminating proxy must forward verified HTTPS through trusted Nginx config;
untrusted X-Forwarded-Proto/X-Forwarded-For headers are intentionally ignored.

There is no remote shell, broad device wipe, arbitrary APK URL, public test-token
issuer, self-claimed reseller/customer ownership, or reseller update source.
App check-ins are foreground-only. Offline/stopped apps cannot be awakened by this
panel, and external players/other apps are not controlled by the app's policy gate.
Never reuse a database password previously pasted into a chat or screenshot.
